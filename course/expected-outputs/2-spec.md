## Spec: Promo codes at checkout

**Goal:** A customer can enter one promo code at checkout to get a fixed percentage off the whole order. Engineering maintains the list of valid codes.

**Acceptance criteria** (each one is a test someone could write)
1. Given a code `SAVE10` set up as 10% off, when `api.checkout({"items": {"tshirt": 2, "mug": 1}, "promo_code": "SAVE10"})` is called, then it returns `{"status": 200, "total_cents": 4680}` (5200 minus 10%).
2. Given a checkout payload with no `promo_code`, when `api.checkout` is called, then the result is the same as today (the existing tests in `tests/test_shop.py` pass unchanged).
3. Given a `promo_code` that is not in the code table (including one engineering has removed), when `api.checkout` is called, then it returns `{"status": 400, "error": "invalid promo code: <code>"}` and no total.
4. Given a `promo_code` that is not a single string (for example a list of codes), when `api.checkout` is called, then it returns status 400. Only one code is allowed per order.
5. Given the code table in `shop/repo.py`, when engineering adds a `code: percent` entry, then that code works at checkout with no other change. Removing the entry makes the code invalid, as in AC 3.

**Out of scope** (pruned, and why)
- "All kinds of deals" (fixed amount off, buy-one-get-one, per-product discounts, minimum spend): the next campaign only uses X% off the whole order.
- Combining several codes on one order: one code per order.
- Expiry dates, usage limits, once-per-customer rules: no expiry for now, engineering removes a code when its campaign ends, and the shop has no customer accounts.
- An admin endpoint or any other way for Marketing to create codes: engineering adds about three a quarter by editing `repo.py`.
- A discount base class, rules engine or plugin registry: there is only one kind of discount (AGENTS.md: no abstraction without a second real use).
- Recording which orders used a code: nothing in the answers needs it.

**Touches:** `shop/repo.py` (code table and lookup) · `shop/service.py` (apply the percentage to the order total) · `shop/api.py` (read `promo_code`, return 400 for an invalid code) · `tests/test_shop.py`

**Still open for human judgement:**
- **Rounding:** when the discount isn't a whole number of cents (for example 15% off 1999 is 299.85), should it round down, round up, or round to nearest?
- **Capital letters:** should `save10` work the same as `SAVE10`?
- **Allowed percentages:** must the percentage be between 1 and 100, and should a bad entry be caught by a test or left to code review?
